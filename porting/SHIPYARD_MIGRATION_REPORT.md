Candidate choice is not a parity assertion. An optimization is “saved” only after its selected implementation is the compiled Shipyard source in both active consumers and its regression test remains attached.

## Separate gates

- Source identity: same physical Shipyard translation unit or include for both consumers.
- Build path: project manifests and link maps identify that source; no generated rewrite or shadow.
- Behavior: host contracts and Xenia scenarios recorded per subsystem, without treating compile as execution.
- Hardware: physical-console observations recorded separately. Current Shipyard migrations have no new retail validation.
- Publication: per-file provenance and compatible rights still unresolved. No public-release claim.

Build-chain efficiency is a separate measured build-path gate. The shared Shipyard sharder drove both Smash projects with eight concurrent MSBuild jobs, and a live process snapshot showed seven `cl` and eight `MSBuild` processes. All 16 shards succeeded in the final run; the libultraship and application link receipts identify the exact generated project views, input compile receipts and output hashes. This removes the earlier single-compiler-process bottleneck for this build. It does not establish a clean-state build, wall-time speedup versus a controlled serial baseline, runtime performance or hardware behavior.
