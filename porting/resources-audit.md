# Resource, archive, storage and compiler compatibility audit

Audit date: 2026-09-20. Read-only source comparison against the owned Shipwright 9.2.3 checkout (`cb71e22a79bc5d1f688fa881795bbd93094895fc`) and its LUS (`fdcaf6336776d24a6408d016b0a52243f108f250`). No reference files were changed and no donor generator/test was executed. The only output of this audit is this report. Existing donor test source is evidence of available validation coverage, not a claim that this target passes it.

Path abbreviations in the tables are exact filesystem roots: **M** = `D:/Projects/3Shipsty9.x`; **O** = `D:/Projects/SoH360`; **S** = `D:/Projects/Smash360`. Paths following these abbreviations are relative to that root.

## Decision

Keep modern SoH's ResourceManager, ArchiveManager, factories, SaveManager, Config and CVar behavior. Adapt the reusable Xbox compiler/library substrate from Smash360, with source locks regenerated against the owned target and each changed source transformation reviewed. Old SoH360 is a useful Xbox storage/endian reference, but its bespoke asset manager and older save/config models cannot replace the modern classes.

The pinned modern extraction chain is **ZAPDTR + OTRExporter**. `M/CMakeLists.txt:176` adds ZAPDTR, line 177 adds OTRExporter, and line 207 invokes `OTRExporter/extract_assets.py` with `--custom-otr-file soh.o2r`. `M/OTRExporter/OTRExporter/ExporterArchiveO2R.cpp` uses libzip. There is no reason to introduce Torch from BattleShip. Runtime O2R support does not remove OTR support: `M/CMakeLists.txt:162` enables MPQ support, `M/libultraship/CMake/dependencies/common.cmake` requests StormLib v9.25, and `ArchiveManager.cpp` includes both OTR and O2R implementations.

## Exact source compatibility findings

SHA-256 comparisons against `S/platform/xbox360/cpp-compat/resources/sources.lock.json` found **33 of 41 LUS resource/utility inputs exactly match M and the actual S upstream files**. Eight differ:

- `include/ship/resource/archive/Archive.h`, `src/ship/resource/archive/Archive.cpp`: S adds archive manifest parsing, script binary/dependency fields and signature/checksum stub APIs. M does not have them. The donor's exact `ArchiveManifest` and `binaries` loop anchors must be omitted when adapting to M; importing them would change target scope.
- `include/ship/resource/File.h`: S adds `BufferOffset`; M does not. The donor initializer transform requires this field and will fail on M.
- `src/ship/resource/ResourceLoader.cpp`: S uses the offset into the original buffer; M copies the legacy header and strips it from the file buffer. Preserve M's shape initially. M constructs the header slice before checking length, so the existing check cannot safely reject a too-short original buffer; a separate, tested correctness change should check source length before iterator arithmetic.
- `include/ship/resource/ResourceManager.h`, `src/ship/resource/ResourceManager.cpp`: S adds rvalue path construction and alternate-path comparison optimization. M retains const-reference construction and direct alternate path checks. The existing lowering already has text handling for these variants, but whole-file source locks must be replaced and results inspected.
- `src/ship/resource/factory/BlobFactory.cpp`: S adds 16 bytes of padding for its compressed MIDI overreads and references `AudioDma_Clamp`. This is Smash-specific behavioral work and must not be imported. The donor `constexpr kBlobPadding` anchor is absent in M.
- `src/ship/resource/Resource.cpp`: S removes destructor logging because resources can outlive logging shutdown; M still calls `SPDLOG_TRACE` in `IResource::~IResource()`. The donor generator removes the spdlog include as unused, which is not valid for M's retained destructor. Preserve the include during syntax lowering and separately decide/test shutdown lifetime or the explicit logging correction.

All nine BinaryReader/BinaryWriter/MemoryStream/Stream/endian input paths were independently compared with S. **Seven match exactly**; only `MemoryStream.h` and `MemoryStream.cpp` differ, principally the S offset constructor used by its no-copy resource header path. `BinaryReader.cpp`, `BinaryWriter.cpp`, their headers, `Stream.h/.cpp`, and `endianness.h` are exact matches. This is the smallest suitable initial compiler projection, but the new generator must own M hashes and M source locations rather than invoke the donor script in place.

For Config/CVar, `Config.h` and `ConsoleVariable.cpp` match S exactly, while `Config.cpp` and `ConsoleVariable.h` differ. `prepare_config_xdk.py` also depends on a separately locked audio integration patch and the Prism/range lowering support. It is not an independent drop-in script.

Do not run donor generators against reference roots: their `ROOT` globals resolve into S, generated outputs go into S scratch, and some transitive scripts import compatibility packages. Copy/adapt reviewed generators into owned build tooling with explicit inputs/outputs, fail-closed locks and source mappings. Preserve separation of syntax lowering from correctness fixes (`prepare_resources_xdk.py` already models this as `transform()` versus `corrections()`).

## Specific correctness candidates worth preserving

The donor's `corrections()` isolates useful generic repairs: drain/reset resource pool before mutex/cache members are destroyed; lock failed cache insertions; atomically remove a cache entry and destroy its resource after unlocking; handle a queued batch using the same resource processing function when only one worker exists; initialize ZIP handle, bound ZIP size to target `size_t`, require exact reads, use RAII for entry closure, and discard/clear a failed-close handle; normalize folder prefixes consistently; avoid `operator[]` insertion on missing archive lookups. These are concrete source-derived hazards also visible in the M shapes, not speculative reasons to replace its architecture.

M's `O2rArchive.cpp` is byte-identical to donor input, including constructor without handle initialization and read path that logs a negative read yet subsequently marks loaded. Review and port those corrections with malformed/read-failure fixtures. Extend coverage to `WriteFile()` lifetime/reopen semantics and concurrent access rather than assuming donor test breadth is exhaustive.

Xenon native-endian detection is immediately actionable. M's endian header recognizes GNU byte-order macros/`__BIG_ENDIAN__`; it does not explicitly recognize the XDK `_XBOX && _M_PPC` condition. S's binary generator adds that condition to both native enum selection and `IS_BIGENDIAN` detection. Keep `BSWAP` unconditional and `BE/LE` conversion direction correct; the reader compares serialized endian with native endian already.

Old storage is a strong donor at the boundary: `O/platform/xbox360/platform.cpp:405` creates a temporary file, validates the full write, flushes it, replaces the destination using `MoveFileExA` and calls `XContentFlush`. Its worker owns serialized bytes and reports completion after durable write. M copies `SaveContext` before `detach_task`, holds `saveMtx` while serializing, then updates metadata/hooks; preserve that snapshot contract and prevent storage callback changes from racing game data. Porting the old save model wholesale would lose modern sections and version migration.

## Validation limits and actual gating conditions

This audit did not build or run M on Xenia. Donor object files, logs and existing test code are not fresh M verification. No source-derived fundamental blocker was established in these subsystems. C++20 lowering, API additions, endian corrections, modern save parity and Xbox storage integration are implementation work with concrete validation gates.

The immediate gates are: a reproducible owned dependency/input lock; XDK compile/link of the retained real binary/resource/config classes; complete reached JSON/filesystem/pool API coverage; legal user-supplied target-version assets generated by the modern ZAPD chain; and Xenia tests proving resource loading, saving, reloading and bounded memory behavior. Missing output artifacts or an unimplemented API does not justify reverting to old SoH or dropping functionality. Asset extraction on a host can produce runtime input while Xbox extraction integration is implemented; the modern `OTRGlobals.cpp` extraction UI/tasks and `soh/CMakeLists.txt` ZAPD linkage mean any choice to omit on-device extraction needs explicit scope agreement, not accidental removal during portability work.

Suggested first acceptance sequence: native binary tools fixture; native libzip/StormLib archive fixture; real ResourceManager plus factories (single and multiple worker configurations); real Config/CVar plus updater fixtures; modern SaveManager with vanilla/MQ/randomizer fixture and failure injection; gameplay transitions, mod precedence, restart persistence, and repeated load/unload memory measurement in Xenia.
